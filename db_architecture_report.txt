DATABASE ARCHITECTURE REVIEW — Migration 202611040004
================================================================================

1. TABLE: public.payout_items
   New column: replaces_payout_id UUID (nullable, FK to payout_items(id) ON DELETE SET NULL)
   New index: uq_payout_items_replaces_payout (WHERE replaces_payout_id IS NOT NULL)
   Purpose: Traceability — links a reissued payout to its original disputed row.

2. RPC: public.admin_request_payout_reconfirmation(p_payout_id, p_admin_notes)
   Moves a disputed row → status = pending_confirmation
   Same row, same UTR — organizer receives confirmation request again
   Wallet NOT debited (only debited when organizer accepts)
   Returns: { ok, payout_id, amount, status, message }

3. RPC: public.admin_reissue_disputed_payout(p_payout_id, p_utr, p_payment_method, p_admin_notes)
   Full workflow:
   a) Validate admin auth
   b) Load old payout row (FOR UPDATE) — was MISSING, caused runtime errors
   c) Validate community lock
   d) Check duplicate UTR (reject if already active)
   e) Insert new row: status=pending_confirmation, same amount/event/beneficiary/currency, new UTR, replaces_payout_id = old id
   f) Cancel old row: status=cancelled, resolved_by_admin, resolved_at, resolution_notes
   g) Two audit log entries: reissued + manual_payout_recorded (with reissue_of link)
   h) Return: { ok, old_payout_id, new_payout_id, amount, old_status, new_status, message }
   Amount parameter OMITTED from caller — reissue uses old row's amount, not a new amount.

4. RPC: public.admin_request_payout_reconfirmation (additive)
   New column wallet_debit_amount appears in statement output:
   - success → amount
   - all other statuses → 0

5. RPC: public.get_admin_financial_statement (additive)
   New columns in raw_transactions CTE projection:
   - wallet_debit_amount: CASE WHEN status='success' THEN amount ELSE 0 END
   - reserved_amount: CASE WHEN status IN ('pending_confirmation','disputed') THEN amount ELSE 0 END
   - replaces_payout_id: pi.replaces_payout_id
   - running_balance computed in with_running_balance CTE:
       SUM(money_in - CASE WHEN transaction_type='refund' OR status IN ('success','processed') THEN money_out ELSE 0 END)
       OVER (ORDER BY created_at ASC)
   - Output projection adds: wallet_debit_amount, reserved_amount, replaces_payout_id, running_balance
   All existing keys retained; new keys NULL for pre-migration rows (callers use COALESCE).

6. RPC: public.get_organizer_financial_statement (additive)
   Same additive columns as admin statement, plus:
   - running_balance: same window function expression
   - Output: wallet_debit_amount, reserved_amount, replaces_payout_id, running_balance
   Authorization: community_owner OR community_team OR admin_user (expanded from just owner)

7. WALLET SEMANTICS (unchanged but clarified)
   - available = wallet_balance - SUM(pending_confirmation) - SUM(disputed)
   - Release is automatic when status becomes cancelled
   - Wallet debited ONLY on organizer_confirm or admin_resolve('confirm_received_payout')
   - Never debited on dispute, reissue, or cancel
